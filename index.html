3 Train

Model layout

These are compile-time settings in the sketch (INPUT_SIZE, CONV1_FILTERS, CONV2_FILTERS). Copy the lines from section 2 into the sketch after changing them. The 3x3 kernel is fixed in the firmware loops. Images on the card stay 240x240, so changing the size needs no new photos, only a retrain. The size must be even because of the 2x2 max pool. Cost grows with the square of the input size, in the browser and on the device.

Connectivity (graph-theory model type)

Only the conv1 to conv2 channel connections are constrained. Conv1 reads the RGB image and the classifier reads every conv2 filter, so island separation holds through the two conv layers only. A "bridge" is one cross-island conv1 channel to conv2 filter connection (one 3x3 kernel = 9 scalar weights). Model D trains gates on all candidate bridges, keeps the top K by gate score, freezes that topology and fine-tunes. Changing the type never reinterprets weights already in memory: the next Train starts fresh.

4 Graph workbench

Research tools for the conv1 to conv2 channel graph. Every result is labelled with the dataset split it was measured on. There is no separate test set: the validation images are used only to look at results, never to pick bridges (Model D picks them from gate scores learned on the training images). Structure, weights and ablations are evidence about this one trained model, not proof that a filter means something.

3D: drag to orbit, shift-drag or right-drag to pan, wheel or pinch to zoom, hover to light up one node's forward and backward connections, click for details. Sphere size = degree (number of conv1 to conv2 connections). Glow halo or heat colour = bridge importance (betweenness: how many shortest paths between channels run through it). Tube thickness = mean |weight|, so pruned or near-zero connections thin out or vanish. Red glowing arcs = bridges between islands (fixed in C, selected in D), grey faint tubes = candidates, grey with ✕ = switched off. Flow view: colour = activation of the last image (blue cold, red hot), particles run RGB → conv1 → conv2 → classes.

2D line styles: solid = within-island edge (island colour), long dashes with B labels = bridge, dotted grey = candidate or unselected bridge, dash-dot with x = marked for ablation, thin grey = classifier edge. Nodes are channels; each conv edge holds one 3x3 kernel.

What future firmware must implement


  

  

    
One tuning plan, two authors. Every move below (encourage, reduce, freeze or prune an island, a channel or a bridge) is the same small record whether you click it, the coach proposes it, or you paste it as JSON. The plan changes how the next training steps treat those weights: encourage = learning rate x2, reduce = x0.5 and the weights shrink slightly, freeze = x0, prune = a bridge is removed for good. The forward and backward pass are not touched.

3. Auto-coach

    
Each round: the coach picks its best moves, trains the epochs above with them, then trains the same epochs from the same starting point without them (same shuffling). It keeps the moves only if validation accuracy is not worse than the control (within the margin below) and loss is not clearly worse. Rejected moves are not tried again. Every decision lands in the journal, so you can read it, undo it, or redo it by hand. Costs two training runs per round.

7 Save

  

    
    
    
    
  

  

    
SD folder mode: the existing weights file is copied to myWeights.bin.bak first, then the new one is written. A config.json with the class names and layout is written next to it. The firmware reads the class names from it at boot. NUM_CLASSES, INPUT_SIZE and the filter counts always come from the compiled sketch.

    
Zip mode: Save weights keeps the model for the zip. Save .zip downloads header/myWeights.bin (and images if ticked) in the SD card layout.
